# TIP-045 — Show the newest available candle in chart captures

## Behavior

`capture_live_chart(chart_id=...)` sends MT5's `End` chart shortcut to the verified, focused chart view after the chart becomes renderable and before `PrintWindow` captures it. This applies to both the default 960×540 image and `aspect_ratio="native"`, including charts temporarily restored from a minimized state. The selected chart stays at the newest available bar after the screenshot; the user's Auto Scroll setting is not changed. Other charts are not navigated.

The existing native execution lease still serializes chart operations. Key messages use bounded Win32 dispatch to the GUI thread's focused child, after verifying its parent chart and exact executable. If another chart owns focus, the requested chart is activated and the prior selection restored after capture; if focus cannot be verified, capture fails explicitly. The 16:9 and minimized-chart paths still restore placement and minimized state. The PNG/ImageContent, hash-bound export, default 16:9 and 79-tool catalog are unchanged. Version `0.2.41`, build `TIP-045`.

The newest *available* candle depends on the MT5 price feed. Sending `End` establishes a navigation request but does not prove that the client processed the shortcut or that the broker supplied a newer candle. The user-visible screenshot is the acceptance evidence for its right edge.

5. Check chart IDs, placement, minimized states, active selection, health, locks and A/B/C tunnel readiness after capture. The selected chart's horizontal scroll position is intentionally left at the latest bar.

The first TIP-045 implementation sent End to the MDI frame. A live XAUUSDm/M1 capture remained on 23 September 2026 while MT5 had M1 bars through 25 September 20:57 UTC. Sending or posting the key to the parent frame did not navigate. The chart's keyboard focus was on an `AfxFrameOrView140su` child of chart `67352`; bounded End down/up messages to this exact-process child produced a screenshot with the 25 September candles and newest bar near the right edge. ## ChatGPT tool snapshot blocker (26 September 2026)

Business C's direct acceptance stopped before chart listing: runtime `server_info` reported 79 server tools and 78 expected model-visible tools, but the chat did not expose the six live functions above. Guards were READY/idle and A/B/C each had one process with `200/200`; `capture_live_chart` was called zero times. This chat independently exposed 72 TunnelVibemq5 functions, also missing those same six. The reported `TypeError` used a noncanonical code-mode function name, so it is not sufficient evidence by itself; the actual tool registry comparison confirms the missing surface. Direct MCP capture, default 16:9, export, inline delivery and layout rollback remain **BLOCKED** on this connector installation, separate from the verified Windows production-path screenshot.

OpenAI documents that an approved MCP app keeps a frozen snapshot of tools and inputs. For a published **Business** app, tool changes require creating a new app, scanning the current tools and publishing it; restarting the MT5 Bridge alone does not update that snapshot. Keep the old app until the new draft has passed direct acceptance. For **Enterprise/Edu**, an admin can use Workspace settings → Apps → Action control → Refresh, then review and enable the new actions. See [Developer mode and MCP apps in ChatGPT](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt).

In each affected account/workspace, verify the newly selected app exposes the six live tools before calling any chart tool. Test Business C in C's own chat; A/B tunnel `200/200` does not prove their ChatGPT tool schemas. Do not use backend tests as a substitute for direct MCP acceptance.
